内部構造アーキテクチャ & VMwareスタック対比

HPE Morpheus VM Essentials (VME) は、Linux KVMを中核エンジンとし、Morpheusの管理オーケストレーションを組み合わせたエンタープライズ仮想化スタックです。

1. VMware vSphere コンポーネントとの対応関係

機能レイヤー VMware vSphere HPE Morpheus VM Essentials
集中管理プレーン vCenter Server VME Manager (アプライアンスVMとして稼働)
ホストエージェント vpxa / hostd HVM Agent (ManagerのRPC要求を受信・実行)
仮想化抽象化API ESXi Kernel Direct API libvirt (KVM/QEMU操作の標準抽象化レイヤー)
ハイパーバイザー/実行 VMkernel / VMM KVM (カーネルモジュール) + QEMU (VM空間プロセス)
クラスタHA/ロック調停 vSphere HA (FDM) / VMFS ロック Pacemaker + DLM (Distributed Lock Manager)
仮想スイッチ vSphere Standard / Distributed Switch Open vSwitch (OvS)

2. コントロールプレーンの制御フロー

API連携フロー (VME Manager → VM起動)

  • Step 1: 管理者がVME Manager GUI/APIで操作を実行
  • Step 2: VME Managerから各ノードのHVM Agentへ制御要求を発行
  • Step 3: HVM Agentがホストローカルのlibvirt APIを呼び出し
  • Step 4: libvirtがQEMUプロセスをフォークしKVM経由でCPU/メモリを仮想化

技術的特徴と分離性

OSネイティブなKVM/libvirtスタックを標準採用しているため、プロプライエタリなブラックボックスが少なく、Linux標準ツールやスクリプトによる監視・診断と高親和性を持ちます。

リソース抽象化設計（グループ・クラウド・クラスタ）

VMEはCMP（Cloud Management Platform）であるMorpheusの思想を継承しており、VMwareとは階層定義のパラダイムが異なります。

1. 抽象化オブジェクトの階層構造

グループ (Group)

テナント・組織の論理境界

  • ユーザーやロールに対する権限付与のスコープ単位。
  • 「誰がどのリソースにアクセスできるか」を定義。
  • 組織（例：第1開発部、基幹インフラ課）ごとに切り分け。

クラウド (Cloud)

インフラ基盤の統合登録単位

  • VMEクラスタそのものを管理単位としてマッピング。
  • 将来的なパブリッククラウドや他仮想基盤とのハイブリッド統合点。
  • クラスタの物理リソースの包含コンテナとして機能。

2. クラスタ配置制御（Dynamic Placement）

機能項目 VME の実装仕様 設計・運用上の留意点
Dynamic Placement
(動的配置制御)		 VM作成時、クラスタ内の各ホストのCPU・メモリ空き容量を評価し、最適な物理ホストを自動選定してデプロイ。 vSphere DRS（分散リソーススケジューラ）に相当。初期配置だけでなくリソース偏重時の平準化ポリシーを定義。
クラスタ一元設定 クラスタ定義（NW、ストレージ）を変更すると、クラスタ内の全ホスト（HVM Node）へ自動伝播。 ホスト個別でのネットワーク／データストア設定はアンチパターン。クラスタ単位での構成同一性維持が前提。

共有ストレージ & ネットワーク設計

クラスタ運用およびHA機能（フェイルオーバー）を支えるストレージ・ネットワークスタックの設計基準です。

1. ストレージアーキテクチャの種別と役割

ストレージ種別 採用ファイルシステム / 方式 主用途と設計考慮点
共有データストア
(共有ボリューム)		 GFS2 (Global File System 2)
on iSCSI / FC SAN		 【VM実行領域】
PacemakerおよびDLMにより複数ホストからの排他ロックを協調制御。全ホストでの同時マウントとライブマイグレーションを保証。
イメージストレージ NFS (Network File System) 【テンプレート・ISO保管領域】
VMプロビジョニング時に利用するOSインストールメディアやゴールデンイメージの集中リポジトリ。
ローカルデータストア EXT4 / XFS (Local NVMe/SSD) 【非HA一時領域】
HA対象外のテスト環境、一時スクラッチディスク、キャッシュ用。

2. Open vSwitch (OvS) によるネットワーク統一

クラスタ単位でのネットワーク統一

  • 仮想スイッチ（OvS）はクラスタプロファイルにより一元展開。
  • 全ホストで同一のNIC識別名（Uplink）と論理ネットワークを定義。
  • ノード間でVMが移動してもVLAN・IP構成が維持される設計。

トラフィック分離設計

  • 管理トラフィック: VME Manager ⇔ HVM Agent (RPC/HTTPS)
  • クラスタ心拍 (Corosync): DLM/Pacemaker (極小遅延必須)
  • ストレージ: iSCSI (GFS2) / NFS (別サブネット/Jumbo Frame)
  • VMデータ: 業務VLAN (802.1Q トランク)

移行方式比較 & 検証基盤設計

vSphereからのシステム移行アプローチと、3ノード構成でのPoC（概念実証）・テストベッド仕様です。

1. vSphere → VME マイグレーション方式の選定基準

移行手法 所要コスト / ツール ダウンタイム特性 主な対象システム
Bulk Migration 標準無償 (VME組込) 中（コールド/ウォーム移行） 夜間・休日停止が可能な一般Web/業務APサーバー群
Veeam Plug-In 既存投資活用 (VBR連携) 小〜中（Instant VM Recovery併用） 既存でVeeam運用中の基盤、バックアップ検証を兼ねる場合
Zerto レプリケーション エンタープライズ (Zerto CDP) 極小（数分内のカットオーバー） DB、基幹ERPなど24時間365日稼働のミッションクリティカル系

2. 検証用 3ノードクラスター仕様要件

コンポーネント構成

  • HVM ホスト: 3台（Ubuntu 24.04.2 LTS / KVM）
  • 管理VM: VM Essentials Manager (クラスタホスト上で冗長稼働)
  • 共有ブロック: iSCSI ストレージ（GFS2フォーマット）
  • イメージ共有: NFS ストレージ（ISO / テンプレート）
  • 基底インフラ: DNS / NTP（時刻同期ズレはDLM破綻の主因）

検証必須シナリオ

  • Quorum維持試験: 1ノード強制電源断時のクラスタ稼働継続
  • HA再起動試験: 停止ノード上で動いていたVMの健全ノードへの再配置
  • マイグレーション試験: VMware ToolsからVirtIOドライバへの安全置換
  • ネットワークフェイルオーバー: OvSボンディングポートのリンクダウン試験
