Phase 04 / Storage & HA

ストレージ登録（NFS / GFS2・iSCSI）＆ HAフェイルオーバー制御 Data Stores, iSCSI Multipath, Quorum, Heartbeat & Layout v1.3 HA

HVMクラスタにおける共有ストレージ（NFS Pool / GFS2 Clustered Datastore）の追加手順、 自動マルチパス構成の作法、およびクラスタレイアウト v1.3（Morpheus 9.0.0+）におけるHA制御・フェンシングの仕様です。

1. 共有データストアの登録手順 ＆ 前提条件

UI Path: Infrastructure > Clusters > [対象クラスタ] > Storage > Data Stores
ストレージ種別 登録手順 ＆ GUI入力項目 重要注意点・ハマりポイント（失敗例と対策）
NFS Pool
(NFS共有ストレージ)		 Data Stores > + Add
・Type: NFS Pool
・Server IP: NFSサーバーのIP
・Export Path: 共有ディレクトリパス
・Storage Version: NFSv3 / NFSv4.1
Root Squashing Hazard NFSサーバー側の /etc/exports で no_root_squash の指定が必須です。未設定の場合、ホストからのマウント権限が匿名ユーザー（nobody）に丸め込まれ、アクセス権限エラーで即死します。
  • VM HA要件： NFS共有ストレージでVMの自動フェイルオーバー（HA）を利用する場合、クラスタ内に最低 2 台のホストが必要です。
GFS2 Pool
(HPE Clustered Datastore / iSCSI)		 【重要：正しい追加順序】
1. Storage > iSCSI タブで + Add を選択し、iSCSI Target IP（ポート3260）を登録。
2. 冗長パスが存在する場合は、データストア作成前にすべてのターゲットパスをUIに事前登録（Morpheusが自動マルチパス構成を実行）。
3. Data Stores タブで + Add > GFS2 Pool を選択し、認識された Block Device（例: /dev/mapper/mpathX）を指定。
Data Loss Warning: Reformat ALLOW REFORMATTING の罠： 新規LUNの場合はチェックを入れてクラスタFS（GFS2）で初期化しますが、既存データが残っているLUNでチェックを入れると全データが即時完全破壊されます。
  • 最小ホスト台数：3台必須（クォーラム維持およびスプリットブレイン防止のため）。
  • ホストOS側のストレージリンクは独立した別サブネット・非ルータブル・MTU 9000で構成し、Bondingは禁止（MPIOで冗長化）。

2. クラスタ高可用性（HA）＆ Heartbeat Target / Witness仕様

HAコンポーネント 設定方法 ＆ 動作仕様 レイアウト v1.3（Morpheus 9.0.0+）の設計仕様
Heartbeat Target
(死活監視用ストレージ)		 データストア追加後、一覧の編集（鉛筆アイコン）から HEARTBEAT TARGET にチェックを入れて保存。 各ホストがデータストア上のハートビートファイルを継続的に更新。更新が途絶えたホストを健全な他ノードが検知し、孤立ノードのVMを健全ノード側で自動再起動（フェイルオーバー）します。
Quorum ＆ Fencing
(スプリットブレイン防止)		 Corosync（メッセージング）＋ DLM（分散ロックマネージャー）でノード間合意を維持。
Architecture Shift Pacemaker廃止（マスク化）： Layout v1.3以降、従来のPacemakerは停止・マスクされ、Morpheus Node Agent（morpheus-node-ctl / morpheus-morphd）がHA制御プレーンを担当します。
過半数のクォーラムを失った孤立ノードは、共有ストレージの破壊を防ぐため自動的にフェンシング（隔離・強制リブート）されます。
Witness Worker
(2拠点ストレッチ構成)		 2サイト間（Stretched Cluster）でクラスタを組む場合、第3の拠点に Distributed Worker をデプロイし、クラスタ設定の WITNESS WORKER に指定。
CLI Output Blindspot WitnessノードはMorpheusのアプリケーション層で仲裁を行います。そのため、ホスト上の corosync-quorumtool コマンドの出力結果には Witnessノード自体は表示されない 仕様です（異常ではありません）。

3. ホスト側 正常性確認 ＆ トラブルシュートCLI

※Layout v1.3環境ではPacemakerが停止しているため、pcs status を実行するとエラーのように見えます。以下のコマンド群で状態を確認してください。

確認対象 Linux CLI コマンド 確認ポイント ＆ 期待される出力
Morpheus Agent 状態
(HA制御プレーン)
sudo morpheus-node-ctl status
systemctl status morpheus-morphd
Active: active (running) であること。v1.3のHA監視の中核です。
Corosync クォーラム状態
sudo corosync-quorumtool -s
Quorate: Yes と表示され、参加ノード数が過半数（Nodes: 3 等）に達していること。
DLM 分散ロック状態
sudo dlm_tool status
sudo dlm_tool ls
GFS2のクラスタロックドメインが正常にアタッチされているかを確認。
GFS2 マウント ＆ マルチパス
mount | grep gfs2
cat /opt/morpheus/.mounts
sudo multipath -ll
マルチパス（mpathX）に全経路（Active/Ready）が見え、指定パスにマウントされていること。
